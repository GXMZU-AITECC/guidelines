# C · PR 规范

## C1 目标分支（→ T1）

PR 统一走 **`develop`**；`main` 只用来发版。

## C2 PR 标题（→ T6）

格式统一为 `<type>: <描述>`，type 只有两个：

| type   | 什么时候用 |
| ------ | ---------- |
| `feat` | 加了新功能 |
| `fix`  | 修了 Bug   |

示例：

- `feat: 新增科学计算器模式`
- `fix: 修复 BIN 模式下负数转换错误`

## C3 PR 描述（→ T7）

每个 PR 的描述写清楚三件事：

1. **目的** —— 这个 PR 解决了什么问题、完成了什么效果
2. **改动** —— 改了什么文件、做了什么（列表形式，一目了然）
3. **测试** —— 改完之后测了什么、效果如何（也是列表形式；开发期未完成就如实写现状）

模板（提 PR 时自动加载）：

```markdown
## 目的

...

## 改动

- ...

## 测试

- ...
```

## C4 提 PR 前自查（→ T8）

自查清单随 PR 模板自动加载，逐条勾选：

1. 没有残留的调试代码、多余注释或文件
2. 没删掉不该删的原有代码或注释
3. 新功能或修 Bug 不影响已有功能
4. 没有硬编码的临时数值
5. 自己测过，没有新增报错

## C5 评审与合并（→ T2）

1. 评审人一律来自 `reviewers` team，**仓库与文档里不写个人账号**——换届只改 team 成员；
2. 有写权限的作者自己在 **Reviewers** 里挑 2 名 Reviewer；没有写权限的作者（外部 fork）提完 PR 等就行，由 CODEOWNERS 把评审自动派给 `reviewers`，谁有空谁认领。只在正文打 @ 不算评审；
3. **第二名认领的 Reviewer 给出批准并执行合并**，作者本人的评审无效；
4. 打回时**只引用编号**（如「违反 T6」「见 T8」），不另行撰写拒绝理由；对编号有异议在 PR 内追问；
5. 评审基调：**规范了即可，不苛求完美**——只核对编号的符合性，不对实现方式、代码风格、功能多少挑刺；规范没写的可以建议，不作为拒绝依据。软建议：单个 PR 改动控制在 300 行以内，便于评审。
