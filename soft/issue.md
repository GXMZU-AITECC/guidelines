# I · Issue 规范

Issue 分两类，别混着提：**功能提案**（要做新东西）和**问题报告**（已有的东西坏了）。一题一 Issue，一个 Issue 只谈一件事。

## I1 功能提案（标题以 `feat:` 开头）

| 段 | 写什么 |
| :--- | :--- |
| **要什么** | 一句话说清做完之后能干什么 |
| **怎么用** | 用户视角的操作步骤：点什么、输什么、看到什么 |
| **验收标准** | 满足哪几条算做完，必须可测，别写「美观」「流畅」 |
| **不做什么** | 本次范围之外的东西，防止越滚越大 |

提案人默认拥有这一题：在自己的 Issue 下回一句「认领：姓名 ＋ fork 链接 ＋ 分支名」即占题。别人想做同一件功能，先在这条 Issue 下留言，不另开一条。

## I2 问题报告（标题以 `fix:` 开头）

| 段 | 写什么 |
| :--- | :--- |
| **现象** | 实际发生了什么：报错贴原文，界面问题贴截图 |
| **复现** | 环境与分支、一步步怎么让它复现 |
| **期望** | 按设计本来应该是什么样 |

只写「跑不起来」「不对」而没有复现步骤的，一律退回，不算 Bug。

## I3 通用

- 标题带 `feat:` / `fix:` 前缀，与 PR 一致；
- 讨论跑题的另开 Issue，别在原楼里长篇对线；
- PR 合并时用 `Closes #编号` 关掉对应 Issue，谁提的谁关，别人代关要留言说明。
