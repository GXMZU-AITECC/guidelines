# 协作规范 · 新人必读

两张表管全部：**P 表管人**，**T 表管 PR**。编号越小越严重，打回只写编号，不写理由。

---

## P · 违规处分

处分由**社团组织部**下达，结论写在对应的 Issue 或 PR 里；涉及 GitHub 权限与成员身份的变更，由组织管理员执行。共三档，**高档包含低档全部处分**：

| 档位 | 认定行为 | 处分 |
| :--- | :--- | :--- |
| **P2** | 占题造假：不占题就开工、抢注他人已占的题目、同一题反复刷 PR 占位；带病交付：明知跑不通仍写「已完成」、夹带无关改动掩盖问题、密钥或令牌硬编码入库 | 内部通报；免除现任职务；留置观察（期限由组织部在处分决定里写明，默认一学期） |
| **P1** | 破坏仓库：强推覆盖历史、删主干或他人分支、删他人代码、绕过分支保护直改主干、擅改仓库权限或 Webhook；评审造假：自审自批、找人刷批准、把他人或 AI 整篇生成的代码当作自己写的且不声明 | **P2 全部** ＋ 开除社团，此后不得代表社团参加比赛、不得申报社团的任何资格 |
| **P0** | 外泄内部资产：把仓库内容、设备资料、赛题、Issue / PR 讨论以链接、截图、复制、转发等任何形式给社团外的人，或挂到公开简历、博客、社交账号；私自与社团外人员组队，并在比赛中使用社团的任何知识资产 | **P1 全部** ＋ 上报社团挂靠的人工智能学院及相关指导教师，由老师定夺，酌情下达院级处分 |

## T · 红线

PR 打回的**唯一**依据，只有这 11 条，每条在 PR 页面上都一眼可判。建仓与交付要求不在这里，见下。

| 编号 | 红线 |
| :--- | :--- |
| **T1** | 没有提案就开工：本 PR 没有对应的功能提案 Issue，或提案不是你本人占题的 |
| **T2** | diff 里出现密钥、令牌、账号口令、个人数据——出现即打回，并按 P2 处理 |
| **T3** | 夹带：一个 PR 里混了不相干的功能或重构，或提交了构建产物、模型权重、日志、依赖目录 |
| **T4** | 目标分支不是 `develop` |
| **T5** | 没 rebase 最新 `develop`，或存在冲突 |
| **T6** | 评审不合流程：须 2 名 Reviewer 评审，由**第二名认领的 Reviewer** 批准并合并；作者本人的评审无效，只在正文打 @ 不算 |
| **T7** | 标题不是 `feat:` / `fix:` 开头 |
| **T8** | 描述缺三段：目的、改动、测试 |
| **T9** | 自查清单没有逐条勾选 |
| **T10** | 该仓已配自动检查（CI），本 PR 未通过 |
| **T11** | 分支名不是 `feature/` 或 `bugfix/` 前缀 |

**引用写法**：`违反 T6`、`T7、T8`、`见 T2`。对编号有异议在 PR 里追问，不额外写拒绝说明。表外的一切都不构成拒绝依据——**规范了就行，不挑刺**；通用工程实践（分支模型、提交信息、代码风格、许可选择）不作规定。

**Issue 怎么写**：提 Issue 时按表单填。功能提案写清「要什么 / 怎么用 / 验收标准 / 不做什么」，问题报告写清「现象 / 复现 / 期望」，一题一 Issue。没有复现步骤的问题报告退回。
