# 协作规范 · 新人必读

全社只有两张表：**P 表管人**，**T 表管 PR**。编号越小越严重。
评审打回只写编号，不写理由；表外的一切都不构成拒绝依据——**规范了就行，不挑刺**。

---

## P · 违规处分

踩线即处理，与 PR 无关。技术部部长提出，组织管理员复核，结论写在对应 Issue 或 PR 里。

| 编号 | 行为 | 处分 |
| :--- | :--- | :--- |
| **P0** | 外泄内部资产：把仓库内容、赛题、Issue / PR 讨论以链接、截图、复制、转发等任何形式给组织外的人，或挂到公开简历、博客、社交账号 | 移出组织，当期考核资格作废；上报人工智能学院指导教师 |
| **P1** | 破坏仓库：强推覆盖历史、删主干或他人分支、删他人代码、绕过分支保护直改主干、擅改仓库权限或 Webhook | 收回全部写权限 1 个月并还原内容；再犯清退 |
| **P2** | 评审造假：自审自批、找人刷批准、把他人或 AI 整篇生成的代码当作自己写的且不声明 | 当期 PR 作废，考核顺延一轮；已入社者由技术部通报 |
| **P3** | 占题造假：不占题就开工、抢注他人已占题目、同一题反复刷 PR 占位 | 题目收回，重新排队 |
| **P4** | 带病交付：明知跑不通仍写「已完成」、夹带无关改动掩盖问题、密钥或令牌硬编码入库 | PR 打回并书面说明；密钥立即轮换，造成实际损失的按 P1 处理 |

---

## T · 红线

PR 打回的**唯一**依据。以下每一条自身即完整规则，不必另查条款。

| 编号 | 红线 |
| :--- | :--- |
| **T0** | 主干受保护：`main`、`develop` 只能经 PR 合并进入，禁止直接 push、强推、删分支 |
| **T1** | PR 只提向 `develop`；提向 `main` 一律拒 |
| **T2** | PR 必须有 2 名 Reviewer 评审，**第二名 Reviewer 一并给出批准并合并**；作者本人的评审无效，只在正文打 @ 也不算。作者没有写权限、assign 不了的仓，由 CODEOWNERS 自动指派、Reviewer 自行认领补上 |
| **T3** | 仓库长期分支只有 `main` 与 `develop` |
| **T4** | 分支名只能用 `feature/` 或 `bugfix/` 前缀 |
| **T5** | 提 PR 前必须 rebase 最新 `develop`；有冲突不收 |
| **T6** | 标题必须以 `feat:` 或 `fix:` 开头 |
| **T7** | 描述必须写全三段：目的、改动、测试 |
| **T8** | 自查清单必须逐条勾选 |
| **T9** | 先提 Issue 再动手：功能提案写清「要什么、怎么用、验收标准、不做什么」并声明占题；没有提案直接来的 PR 不收 |
| **T10** | 一个 PR 只做一件事：不顺手重构、不碰无关文件、不夹带构建产物与日志 |
| **T11** | 项目仓 README 必含五段：项目简介、设备依赖、环境配置、使用方法、维护团队（写 team 名，不写个人）；规范仓与训练场不适用 |
| **T12** | 项目仓必须有 LICENSE，默认 MIT；派生 GPL / Apache 代码沿用上游许可证 |

**引用写法**：`违反 T6`、`T7、T8`、`见 T2`。对编号有异议，在 PR 里追问，不额外写拒绝说明。
