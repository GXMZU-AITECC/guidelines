# 人工智能科技社 GitHub 协作规范 · AITECC

> 全部规范采用**章节编号**。评审拒绝时**直接引用编号**（如「违反 B3」「见 C4-2」），不单独撰写拒绝理由，成员自行查阅对应条款；对条款有疑问可在 PR 内追问。

## 强制条款总表（共 12 条）

评审与合并**只核对下表 12 条**；表外条款均为**软建议**——期望遵守，但不作为拒绝依据。单一 repo、小团队，规范贵在执行：条目越少，越有人读。

| #  | 条款    | 一句话                                                                   |
| -- | ------- | ------------------------------------------------------------------------ |
| 1  | **A2**  | 分支模型：`main` 发版 / `develop` 开发                                   |
| 2  | **B1**  | 开发流程：fork → 拉 `feature/...` 分支 → 向 `develop` 提 PR              |
| 3  | **B2**  | 分支命名：`feature/...` / `bugfix/...`                                   |
| 4  | **C1**  | PR 统一目标 `develop`                                                    |
| 5  | **C2**  | 标题用 `feat:` / `fix:` 前缀                                             |
| 6  | **C3**  | 描述三段：目的 / 改动 / 测试                                             |
| 7  | **C4**  | 提交前自查清单（PR 模板逐条勾选）                                        |
| 8  | **C5**  | 评审与合并：**Reviewers assign ≥2 人**、≥1 批准、项目负责人合并、拒绝只引条款编号 |
| 9  | **D1/D2** | 权限角色与申请                                                          |
| 10 | **D3**  | 内部资产与保密                                                           |
| 11 | **E1**  | README 必含                                                              |
| 12 | **E2**  | LICENSE（MIT）                                                           |

软建议包括：A1 仓库命名、B3 代码注释、B4 可运行（WIP 容忍）、E3 依赖文件、F 设备关联、G 学术关联等——场景出现时遵守，评审不卡点。

3. 规范更新后会同步在社团群、GitHub 组织公告通知。
